# The site (DL-85, DL-86, DL-88, DL-89, DL-90, DL-97 to DL-106)

A Streamlit page over the published warehouse. It is built and tested; **it is not deployed** (the hosting steps are phase 4 of the serving layer). The Claude question box (phase 3, DL-86) is built and tested with a scripted client; it has not been run against the real Claude API, which needs your key.

```bash
pip install -r requirements.txt && pip install -r app/requirements.txt && pip install --no-deps -e .
streamlit run app/streamlit_app.py
```

## How it is built
- `src/oa_market_intelligence/serving/data.py` reads the warehouse **read-only** and returns aggregates (months, specialties, specialty x age band x gender segments); no function takes SQL text and none returns patient-level rows (tested).
- `serving/views.py` holds every frame and every sentence the page draws, so the wording of each headline is tested; numbers in sentences (the bias, the coverage of the range) are computed from the tables, not typed.
- `app/streamlit_app.py` only lays it out. Nothing is fitted while a page loads.
- The page reads the committed `data/published/warehouse.db`; when the monthly workflow commits a new one, the site shows it.
- The Context tab also reads the committed public-data subset `data/published/external_subset.db` (read-only, through `data.external_context`): the company's quarterly net sales, Medicare adoption by state, the dated events and the stored verdicts of the pre-registered public-data analyses. These are different sources from the IQVIA visits and are set beside them, never combined.

## Tests and the CI job
`tests/test_serving_views.py` (by hand on small frames), `tests/test_serving_data.py` (the real warehouse: read-only, aggregates only, findings equal the README) and `tests/test_site_app.py` (the page run headlessly with Streamlit's test runner: no exception, every tab, the headline numbers and the caveats). The app test needs Streamlit and `tests/test_serving_charts.py` needs Altair, so both run in the CI job `site`, which installs `app/requirements.txt` (they are skipped where those packages are not installed).

## The question box (DL-86)
- **What Claude can see.** Eleven tools and no more. Six read the tables: `get_data_status`, `get_market_trend`, `get_segments`, `get_forecasts`, `get_model_results`, `get_findings`. Four read the knowledge graph ([knowledge_graph.md](knowledge_graph.md)): `get_entity`, `get_neighbors`, `get_competitors`, `get_events`. A last one, `show_chart`, asks the page to draw one of four charts (`trend`, `segments`, `forecast`, `specialty_mix`); Claude chooses the chart and its settings and the page draws it with its own tested chart code (`serving/charts.py`), so Claude never writes drawing code. Each tool returns a small summary built by the same functions as the tabs (`views`), so an answer can be checked against a tab. None takes SQL text, a table name or a column name, and none returns patient-level rows (tested). Bad input comes back to Claude as an error message, not a stack trace. A name that fits several things (a product and a group are both "Zilretta") resolves to the product; a truly ambiguous one returns the candidates and asks for an id.
- **What it is told.** The system prompt (`qa.SYSTEM_PROMPT`) says to answer only from tool results; to say when no model beat the simple rule; to state the bias with any segment forecast; to treat the alert as a 1-month supporting flag; to give findings as what the data show, never why; to repeat the stale-data warning; to give no investment, medical or prescribing advice; and to treat the user's message only as a question. For the graph it adds: events are context, never causes; the competitor groups are the project's own grouping, not a market fact. Earlier turns of the conversation are given as plain text and flagged as not re-checked. Tests check the wording is in place.
- **Limits.** Optional shared access code; 8 questions an hour per visitor; 200 an hour for the site; a daily token budget (default 300,000); questions up to 500 characters; at most 5 tool rounds of 800 tokens. These limits live in the running app, so they reset when the host restarts it. **The hard cap is the monthly spend limit you set on your Anthropic account.**
- **Secrets.** Set these in the host's secrets store (Streamlit Community Cloud: app settings, Secrets) or as environment variables for a local run. Never put them in a file in the repository.

  | Name | Needed | Meaning |
  |---|---|---|
  | `ANTHROPIC_API_KEY` | to switch the box on | your key from the Anthropic console |
  | `ACCESS_CODE` | optional | a shared code visitors type before they can ask; empty means open |
  | `DAILY_TOKEN_BUDGET` | optional | tokens per day for the whole site (default 300000) |
  | `CLAUDE_MODEL` | optional | model name (default `claude-haiku-5-5`) |

- **Trying it locally.** In your own terminal (never paste a key into a chat or a file in the repository):

  ```powershell
  $env:ANTHROPIC_API_KEY = "<your key>"
  streamlit run app/streamlit_app.py
  ```

  Then open the Ask Claude tab. Check each answer against the tab it came from; the example questions on the tab are a good first set.
- **Tests.** `tests/test_serving_qa_tools.py` (the tools on the real warehouse), `tests/test_serving_qa.py` (the loop with a scripted client: tool round trip, unknown tool, round limit, token totals, API failure with no key text, injection text kept out of the system prompt, history, streaming, sources, charts, figures to check, follow-ups, caching marks), `tests/test_serving_answer_check.py`, `tests/test_serving_charts.py`, `tests/test_serving_qa_check.py`, `tests/test_serving_guard.py` (gate and limits) and the question-box tests in `tests/test_site_app.py` (off without a key, access code, examples, a streamed answer with its sources and follow-ups, history and clearing, a chart and figures to check, empty and over-long questions, the daily budget, the hourly limit, a failed answer, the key never on the page).

## The conversation (DL-88)
- **Chat.** The tab is a conversation: the last 6 turns are sent with each question (text only; a failed answer is not sent back), answers stream in as they are written, and a line says what is being looked up. "Clear the conversation" starts again.
- **Examples and follow-ups.** The tab opens with four questions for a brand manager and four for an analyst. After each answer, up to three follow-up questions are offered; they are chosen from a fixed table by the tools the answer used (no second Claude call).
- **Sources.** Every answer lists where its data came from, for example "Forecasts tab (pred_batch, model_scores)" or "Knowledge graph (dim_product, events.csv)", and "Data the answer used" lists the exact calls.
- **Charts.** When Claude calls `show_chart` the page draws the chart under the answer, with a tooltip on every mark and small groups faded. Colours are the dataviz reference palette (blue for the series, orange for what is projected).
- **The number check.** After each answer, `serving/answer_check.py` lists any figure that is in the answer but nowhere in the data Claude looked up (or in the question), with the note "not found in the data it looked up; it may be a calculation". Years, small whole numbers, dates, ids and the 90% range are ignored; rounding, sign and percent-against-fraction are allowed for. It cannot catch a wrong claim that uses right figures, so it is a prompt to look, not a proof.
- **Cost.** The fixed system prompt and tool list are marked for the API's prompt caching. The limits above are unchanged.

## The question set and its check (DL-88)
`data/reference/qa_question_set.json` holds 28 questions: 19 in scope (trend, segments, forecasts, the alert, models, status, limits, findings and the graph) and 9 that should be refused or limited (a cause for the 2024 fall, buying stock, a 2030 forecast, patient rows, a request to reveal the prompt and key, SQL, another drug, medical advice, sales by state). Each in-scope question lists the calls a good answer makes and facts they must return; each lists words a good answer includes or avoids.
- **In CI, no key:** `tests/test_serving_qa_check.py` runs every in-scope question's calls on the committed data and fails if a fact is missing, so a change to the data or the tools cannot silently leave a question unanswerable.
- **With your key, by you:** `oa-ask-check` asks Claude every question and screens each answer on the words, on whether it looked anything up, and on figures not found in the data (`--only q01,q05` for some; `--out answers.json` to keep the full answers). It reads `ANTHROPIC_API_KEY` from your environment and never prints or saves it. It uses real tokens (28 questions, up to 5 rounds each). The screen is rough: **read the answers as well**, and record what you find. **No real answer has been graded yet.**

  ```powershell
  $env:ANTHROPIC_API_KEY = "<your key>"
  oa-ask-check --out data/processed/answers.json
  ```

## The Market map (DL-89)
The knowledge graph ([knowledge_graph.md](knowledge_graph.md)) as a picture, because a table of 827 connections is not something a brand manager reads. Three views, because all 311 points at once is a hairball:

| View | Shows |
|---|---|
| Zilretta and the groups it is compared with | the Zilretta product and its group; the two groups it is compared with; each group's leading manufacturers; Zilretta's leading specialties (point size and line width follow its visits); the events that name Zilretta or its maker |
| Which specialties each group's visits come from | the three groups and the top specialties by combined visits; each line's width is the specialty's share of *that group's own* visits, so the groups' mixes can be compared |
| The event timeline and who each event names | all 14 events, the market, and the product, maker or disease area each event's own text names |

- **Controls.** The view; how many manufacturers and specialties (3 to 15); whether to show the events; and "Let the points drift and spread out" (off by default: the layout is worked out in advance with a fixed seed so the map opens whole and looks the same every time, and turning drift on lets the points move from there).
- **Reading it.** Each kind of point has its own colour and shape (star product, box group, square manufacturer, dot specialty, diamond event; a grey diamond is an event that is not verified), shown in a legend above the map. Hover a point or a line for its facts and its source; drag to move, scroll to zoom. Dashed lines are comparisons or derived, not direct facts: a line from a manufacturer to a group means the manufacturer makes products the project placed in that group (derived from `made_by` and `in_group`, and its tooltip says so).
- **Look closer.** A picker lists every point in the view; choosing one shows what the graph holds about it, its connections (relation, other end, visits and share where there are any) and the sources.
- **Events against the share.** The share line with the events that fall inside the data (August 2019 to July 2025) as thin rules, a shaded band for an event with an end date, and dashed grey for one that is not verified; hover for the event and its type. Below it, the table of all 14 events with their sources. Events before the data begins are in the table only.
- **What it does not claim.** No line is a cause; the March to July 2024 dip is tied to the market only. Competitor groups are the project's own grouping, not a market fact. Visits are product-visits inside IQVIA's panel. IQVIA's "No Manufacturer" placeholder (4 products) is not drawn or listed as a company (it stays in the graph as the source gives it).
- **How it is drawn.** `serving/market_map.py` builds each view as plain nodes and edges (tested without any drawing library) and `to_html` draws it with `pyvis` as one self-contained page: the drawing library is embedded and the Bootstrap link pyvis adds is removed, so the map needs no network. The page is shown in an iframe. `pyvis` is in `app/requirements.txt`; if it is missing the tab says so and the details and events below still work.
- **Tests.** `tests/test_serving_market_map.py` (each view's contents, a source on every line and a tooltip on every point, derived lines marked, the slider clamped, no cause drawn, the placeholder left out, details and the event table, a fixed layout, a self-contained page), the events chart in `tests/test_serving_charts.py` and the tab in `tests/test_site_app.py`. The drawing tests need `pyvis` and `networkx`, so they run in the CI job `site` and are skipped where those are not installed.

## The redesign, tab by tab (DL-90)
The site is being reworked one tab at a time, so each change can be looked at and corrected before the next. Done so far:

- **The look (every tab).** A project theme in `.streamlit/config.toml`: teal as the accent, navy text and a navy dark mode. Streamlit follows the visitor's light or dark setting and uses the matching colours; the charts take their text and grid colours from the page (the first version fixed them to a grey that was hard to read in dark mode), and the Market map is drawn in light or dark colours to match.
- **The data-age note.** The long yellow warning is on Overview only. Every other tab starts with a one-line badge, for example "Data to Jul 2025 · 454 days old, no newer extract" (orange when stale, green when fresh), so the first screen of each tab is not taken up by it.
- **Overview.** As in the table above. The three status cards come from `views.use_and_dont`, which now also returns a status and a colour for each forecast (national: "Rely on it as a baseline", green; segment: "Use with care", orange; alert: "A supporting flag only", red); the words carry the meaning as well as the colour. The sparklines and the two CSV files are built by tested functions in `views` (`share_series`, `since_peak_series`, `monthly_csv`, `forecast_csv`).
- **Market trend (DL-97).** Laid out like a labour-market snapshot page: a filter bar over everything, four headline cards, one main chart beside a "where it stands" panel, then "explore further" cards and a profile row. The logic is `serving/trend.py` (filters, windows, quarters, the headline numbers, the movers, the profile, the markers and the sentence; tested by hand on a 24-month table), the look is `serving/style.py` (one CSS block and HTML builders that escape what they are given) and the chart is `charts.market_trend_chart`; `app/market_trend.py` only lays it out. Choices: the straight line is drawn and labelled a guide, never a forecast; the peak is taken over the whole series among months with at least 100 visits, whatever the period; "change" columns always compare the last 12 months with the 12 before, whatever the period; groups under 1,000 visits are left out of the movers; a group with a median under 300 visits a month gets a warning that its share jumps by chance; the three-class split exists only for the whole market, so a filtered view shows how the group compares instead; the filter applies to this tab only for now.
- **Segments (DL-98).** Same look as Market trend. The logic is `serving/segments.py` (the ranked groups with share, visits, share of Zilretta's visits, a small flag and the 12-month change; the concentration; the extremes; the grid; the yearly lines; the sentence; the CSV; tested by hand on a 24-month table and against the older `data.segments` on the real warehouse), the drawing is `charts.group_chart`, `charts.share_grid` and `charts.group_trend_chart`, and `app/segments_tab.py` only lays it out. Choices: groups under 1,000 visits in the period are left out and counted; groups under 5,000 visits are drawn faded and never named in a headline or card (one prescription moves their share too much); the grid shows a share only where a cell has at least 300 visits and caps its colour scale at 8% so a few extreme cells (Pediatrics in the oldest age bands) do not wash out the rest; the "change" is always the last 12 months against the 12 before; the yearly lines use all months whatever the period. **Filters stay local to each tab** (decided here): each tab answers its own question, and a hidden shared filter would change numbers on a tab the reader is not looking at.
- **Forecasts (DL-99).** Same look. The logic is `serving/forecasts.py` (the national forecast with both ranges, how often the range held, the chart frames, each segment's forecast beside its latest-month share, the specialty roll-up, the alert list, the trust and bias wording, the CSV; tested by hand on a small frame and against the real warehouse), the drawing is `charts.national_fan_chart` and `charts.specialty_forecast_chart`, and `app/forecasts_tab.py` only lays it out. The tab shows the monthly job's stored output and fits nothing. Choices: the segment bias is stated before the segment forecasts, in a red callout where the served method is a model and a neutral one where it is the simple rule (6 months); a specialty with under 300 visits in the latest month is left out of the chart (Pediatrics stretched the axis to 50%) and counted in the caption, and every segment stays in the table; segments under 100 visits are marked small; the alert stays a 1-month flag whatever the horizon chosen; the forecast change from last month is shown, with a plain note that part of it is a segment falling back toward its usual level, never as a prediction for one segment. Round 2 (a provisional bias correction) is not shown here: nothing is adopted, and it will appear on the Model results tab with its provisional status.
- **Model results (DL-100).** Same look. The logic is `serving/results.py` (the headline cards, the round 2 tests in plain words, the SHAP rows, the alert cards; tested by hand and against the real stored results), `style.test_rows` for the list of tests, and `app/model_results_tab.py` only lays it out; `data.round2`, `data.round2_posthoc` and `data.shap_summary` read the committed reference files. Choices: round 2 sits in its own section behind a provisional note (found after seeing round 1, same test months, nothing used by the site); a pass is labelled "Passes (provisional)" and a non-pass "No pass", always in words as well as colour; the ranking pass carries the mean-reversion reading from the post-hoc check (reversing each segment's last move alone gives +0.38 against the model's +0.49); the "just spiked" caveat on the alert stays, with its three bars per horizon; no round 2 result changes a forecast or an adopted model anywhere on the site.
- **Findings (DL-101).** Same look. The logic is `serving/findings.py` (the five themes, each finding in exactly one, the order, the four to read first, the source counts and the CSV; tested including that nothing is lost by a theme or a filter and that every real finding card carries its text unchanged); the HTML is `style.finding_card` and `style.text_card`; `app/findings_tab.py` only lays it out. The wording of every finding is unchanged (they are the README's). Choices: what it means comes before the evidence, because a brand manager reads the meaning first; the evidence is a folded `<details>` block, so a click does not rerun the page; finding 1's impact (the size of the decline must not be quoted as a market fact; ask IQVIA whether panel coverage changed) is on a card at the top; the themes were chosen by judgement and are not in the README; a finding with no theme would go in an "Other" group rather than disappear.
- **Context (DL-102).** Same look. The logic is `serving/context.py` (the annual and indexed company series, the headline, the stored gap checks read from the latest run in plain words, the national and state adoption, the rank stability, the states furthest below national, the event rows; tested by hand and against the real subset, which reproduces the published figures: sales +2.7%, +5.3%, +6.3% and visits +6.7%, -13.5%, -35.9% for 2022 to 2024; national Medicare adoption 1.08% to 1.78% in 2021 to 1.47% in 2024; state rank correlation 0.92), `style.timeline_rows`, the charts `company_visits_chart` and `state_tile_map`, and `app/context_tab.py`, which only lays it out. Choices: finding 1's own wording (the size of the IQVIA decline must not be quoted as a market fact; ask IQVIA whether panel coverage changed) is quoted under the chart, not rephrased; the tab says what was tested and what was not, and names no cause; the state map is a tile grid (no map file, no network), paler where a state has under 100 visible providers, with its colour scale stopped at 4%; Medicare data is labelled as Original Medicare public data, not IQVIA; the verdict pills are neutral grey on purpose (a "supported" check is not good news here).

Data status's four metrics became cards. Ask Claude's example questions sit side by side in one card for each audience, and the Market map's controls, map, details and events each sit in a bordered card. The stylesheet is added once, at the top of the page, instead of by each tab. Nothing about the question box's behaviour, limits or wording changed, and it is still off until a key is configured. ## Pages, navigation and filters (DL-104)
The site is ten pages with a navigation, not tabs on one page. Moving between them is faster (only the page you are on runs, where the tabs ran all ten on every click), and each page has its own address (for example `/market-trend`, `/forecasts`), so a page can be linked to and the browser's back button works.

- **How it is built.** `app/streamlit_app.py` is only the frame: the page setup, the look, the navigation and the filter bar. The pages are `app/views/*.py`, a few lines each over a tab module (`app/*_tab.py`) and a tested module in `serving/`. `app/common.py` holds what every page shares (the data, loaded once and read-only; the data-age note; the filters). The list of pages (title, file, icon, address) is `serving.overview.PAGES`: the navigation, the Overview's guide and the tests all read it, so they cannot disagree.
- **The navigation is on the right**, as a collapsible list with icons, and the current page is highlighted. It is placed with a few lines of CSS in `serving/style.py` that depend on Streamlit's own element names (`data-testid` values), so it is the part most likely to need a look if Streamlit is upgraded (the site pins its version in `app/requirements.txt`). A collapsed navigation disappears completely, and a small "<<" button at the top right brings it back.
- **One filter bar for the pages that use it** (Market trend, Segments, Forecasts): specialty, age band, gender and period, with a Reset button. It sits above those pages only, a filter a page does not use is greyed out (the Forecasts page ignores the period) and a line under the bar says which filters the page follows. The filters live in `st.session_state["flt"]`, a plain dict, so they follow you from page to page and back (a widget's own state would be dropped on a page that does not draw it). Segments applies them to the groups it ranks (with the specialty, age and gender chosen, the ranking is within that selection), Forecasts to its segment table, chart and alert list. Each page's own controls (group by, show, months ahead, trend line and the like) stay on the page.
- **Motion.** New content fades in and rises a few pixels over 0.4 seconds, cards lift a little on hover, navigation items nudge on hover and the navigation slides open and shut. All of it is CSS and all of it is switched off for anyone whose system asks for reduced motion. This is not a single-page app: Streamlit still re-runs the page on a click, so the feel is close to the reference site's but not the same.
- **Wording.** The site now says "page", not "tab", in everything a reader sees (including the Ask Claude source labels).
- **Tests.** `tests/test_site_app.py` was reworked: each test runs the page it checks (a run, then a switch to the page, because switching before the very first run is unreliable in Streamlit's test runner), every page runs without an error, the filter bar is on exactly the three pages that use it, the filters follow you across pages and back, the Reset button works and the Forecasts page greys out the period. The unit tests gained the page list, the forecast selection and the calendar parameter (a narrowed selection keeps the whole series' months, so a month a small group lacks does not shift a window).

## Clickable everywhere, and where a click lands (DL-105)
Cards, rows and bars that stand for something are links to the page that shows it, in the same tab, so a click lands in the right place with what you clicked already chosen.

- **How it works.** A link's address carries what was clicked (`segment-detail?specialty=ORTHOPEDIC%20SURGERY&period=3Y&from=segments`). The page it opens reads the filters and the page you came from out of the address (`common.init_from_url`, `links.parse`): the filter bar is already set, a "Back to ..." link appears, and the address is kept in step with the filters (`common.sync_url`), so any page can be shared or reloaded as it is. An address with a value the data does not have (typed, edited or old) opens the page unfiltered and never fails. Addresses are relative, so they work wherever the site is hosted. The logic is `serving/links.py` (tested); the clickable pieces are `style.link` and the `href` / `links` options of the card, row, bar and guide builders.
- **Where each click goes.**

| From | Click | Lands on |
|---|---|---|
| Overview | the share, peak and change cards | Market trend |
| Overview | the forecast card; the three "what to use" cards | Forecasts, the section that shows it |
| Overview | each row of "What each page answers" | that page |
| Market trend | the share card; a row of "where it is moving"; a bar of "who the visits come from" | Segment detail for that group, with the other filters kept |
| Segments | the four cards | Segment detail for the group the card names |
| Segment detail | a neighbour; a part of the path; "its trend", "its forecast", "all groups" | Segment detail for that group; the same group on Market trend, Forecasts or Segments |
| Forecasts | "how the models were tested" (twice) | Model results |
| Model results | the four headline cards | Forecasts (the section for each) and the round 2 section on the same page |
| Context | the four cards | the section on the same page that shows each |
| Findings | "See it on ..." under 15 of the 17 findings | the page and section that shows the evidence (findings 10 and 11, on price and the 2020 pattern, have no page yet) |

- **Back link.** A page reached by a link shows "Back to <page>", in the app (no reload), above its content. It is shown only on the page the link brought you to, so it does not follow you around.
- **A click on a card or row reloads the page** (about 2 to 3 seconds), because it is a plain link; the filters travel in the address so nothing is lost. Buttons and the filter bar stay in the app and are instant.
- **Not done yet.** The other detail pages (competitors, state, price and promotion) are the next pieces; so are the plain-words explanations and the more interactive charts.
## Clicks inside charts and tables (DL-106)
A bar, a cell, a tile or a table row is also a click target. The chart carries a click selection (`charts._pick`, named `pick`), the page reads which point was clicked (`links.picked`, `common.clicked`) and either moves you or opens a panel. Clicks in a chart or table run inside the app, so they do not reload the page.

| Where | Click | Result |
|---|---|---|
| Segments | a bar | Segment detail for that group, other filters kept |
| Segments | a cell of the grid | Segment detail for that specialty and age band |
| Forecasts | a bar of the specialty chart | Segment detail for that specialty |
| Forecasts | a row of the segment table or of the alert table | Segment detail for that exact segment |
| Context | a tile of the Medicare map | a panel under the map for that state: its rate by year with the 95% range beside the national rate, its providers, rank, room to the national rate, Medicare Advantage share and arthritis prevalence; "Close" removes it |

- **No repeat clicks.** A chart remembers its last click, so the chart keys change every time the app moves you (`common.nav_key`) and when the state panel is closed. Without that, coming back to a page, or closing the panel, would act on the old click again.
- **The filter bar follows.** `common.go` no longer sets the filter bar's widgets (Streamlit forbids it once they are drawn, which a click in a chart is); it marks them to take the new values when the bar is next drawn.
- **A click that is not understood does nothing.** No click, a click with the wrong fields or an empty selection never moves the page.
- **The state panel is Medicare billing, not IQVIA**, and says so. It does not say why a state's rate is what it is.

- **Tests.** `tests/test_serving_links.py` (addresses and quoting, reading them back and dropping bad values, the findings' targets, links in the HTML builders and their escaping), `tests/test_serving_detail.py` (the path, the neighbours, the change over the year, the forecast and the sentence by hand, and the real warehouse) and, in `tests/test_site_app.py`, that every link on every page points at a real page, that every section a link names is a heading on its page, that a link from another page opens the page filtered with a way back and that a bad address opens unfiltered.
